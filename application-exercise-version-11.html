    29. Application exercise: version 11

    29.1. Introduction

    In previous versions of the client/server tax calculation application, the [métier] layer that implements the business rules for this calculation was server-side. We now propose to move it to the client side. What is the benefit? Some of the work previously performed by the server will be moved to the client side. Consider a scenario where a server is queried by N clients; N tax business calculations will be performed by the clients. In previous versions, the server performed these N business calculations. Because it no longer performs the business calculation, the server will respond more quickly to its clients requests and will therefore be able to serve more of them simultaneously.

    The client/server architecture becomes as follows:

    • the [métier] [10] layer has been duplicated as [12] on the client;
    • a new script [main2] [11] has been added to the client;

    The web client will have two ways to calculate the tax for the list of taxpayers found in [3]:

    1. Use the method from the previous version. It uses the server's [métier] and [10] layers. The [main] script will use this method;
    2. simply request the tax administration data from the server ([2-4]) and then use the client-side [métier] and [12] layers;

    We will compare the performance of the two methods.

    29.2. The web server

    The web server directory structure will be as follows:

    • The [http-servers/06] folder is initially created by copying the [http-servers/05] folder. We will indeed retain the features of the previous version 10. We will simply add a new feature to it. This is represented by the presence of a new controller [get_admindata_controller] [1]. The other controller, [calculate_tax_controller], is none other than the old controller [index_controller], which has been renamed;

    29.3. Configuration

    The server will offer two URL services:

    1. [/calculate-tax] to calculate the tax for a list of taxpayers passed in the body of a POST. It therefore corresponds to the URL [/] of the previous version 10;
    2. [/get-admindata] outputs the jSON data string from the tax administration;

    The configuration [config] associates each of these URL with the controller that processes it:

    29.7. The web client

    29.9. Client tests

    In each of the [main, main2] scripts, we log the start and end of the script. This allows us to calculate the script’s execution time. Let’s make some predictions:

    1. the [main] script from the previous version:
      1. creates N threads that run simultaneously;
      2. each thread processes a batch of taxpayers for whom it calculates the tax via a single query to the server;
      3. because the N threads run simultaneously, the N+1 request is launched before the Nth request has received its response. Thus, the N requests cost more than a single request but probably not much more. There are also 11 (the number of taxpayers) business calculations on the server;
    2. the script [main2] from this version:
      1. makes a single request to the server;
      2. performs 11 business calculations locally on the client;

    The business calculations will take the same amount of time whether on the server or the client. The difference will therefore lie in the requests. We can therefore expect the execution time of [main] to be slightly longer than that of [main2].

    We launch the version 11 server, the SGBD server, and the [hMailServer] mail server. On the server side, we set the [sleep_time] parameter to zero so that both tests are run under the same conditions.
